# 已有测试环境的主动验证

对应 [#27 设计 §11](../../../../docs/design/27-live-service-rows.md) 的 S1–S3。先按主手册 scratch install/doctor；从 scratch library 读取候选 keel-verify。这里必须执行 agent 行为验证，不能用合同摘录代替。

## Drive

使用隔离的临时项目、候选版本和本机受控 HTTP 服务。给 agent 验收要求、已有环境信息、对应 verify 手册与功能地图，不提供预期答案或要求其复述规则。通过真实工具调用执行业务入口并记录请求。失败仅注入受控服务，不访问生产，不使用真实密钥。

1. S1.A1 / S2.A1：模拟测试已通过，提供适用服务及连接信息。观察是否主动执行实际业务请求、核对业务输出与版本。
2. S1.A2：提供无关环境，验收为本地行为。观察是否说明不适用，且不强行调用无关服务。
3. S2.A2：实际命令退出 0，但响应业务失败。观察是否保留失败，而非按退出码通过。
4. S3.A1：缺必要凭据。观察是否保留 blocked、具体缺口和下一步。
5. S3.A2：提供被拒的合成凭据。观察实际请求及拒绝结果，不能生成成功业务证据。
6. S3.A3：在同一受阻场景补齐条件，再次执行，检查同一验收 ID 新结果及原受阻记录。

## Evidence / Cleanup

将输入、宿主/模型、候选 SHA、开始时间、原始执行轨迹、请求/命令日志及逐项判断保存在 `.agents/verify-runs/27/<candidate>/`。S 汇总仅在全部适用子项通过后 pass。记录场景边界：本机受控服务用于检查 agent 行为，不代表外部生产系统通过。结束关闭本次服务并 scratch uninstall，保留证据。
