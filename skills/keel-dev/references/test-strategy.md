# 测试选择准则

适用于使用 keel 的各类项目。先明确需求中的可观察结果，再选验证方法；不以改的是代码、文档或 Skill 机械决定测试形式。优先复用项目已有测试和样例，只补真正缺少的回归证据。

## 对象与证明边界

| 要证明什么 | 合适的验证 | 不能据此推断什么 |
|---|---|---|
| 文件、引用、配置或机器字段有效 | 结构、解析、存在性及兼容检查 | 不证明自然语言规则或下游行为已生效 |
| 代码、接口、CLI或界面产生所需结果 | 在相应边界观察返回值、输出、状态或副作用；按需要选 Unit / Integration / E2E | 不能只凭源码含某段文字或命令退出0就推断业务结果正确 |
| 自然语言规则指导了正确决策 | 用代表性输入、可判定预期及禁止结果重放；由未生成回答的评估者独立判断，保留实际回答 | 规则被读取、原句存在、关键词命中或回答自评都不等于决策正确；决策说明也不证明实际业务已执行 |

没有行为变化的等义文案整理，可以复用既有检查或做必要审阅，不为填满“测试”阶段机械新增单测。没有 UI 不等于没有需要验证的行为。

## 写测试前

- 说明测试观察哪项需求回归；找不到可观察差异时，不用重复实现或抄写文档来凑断言。
- 检查两种反例：正确的等价实现/等义表述会不会误报？违反需求的实现/决策能否仍通过？按风险选必要检查，不要求每票新增变异框架或穷举所有测试层。
- 自然语言正文不默认逐句、全文或按关键词锁定。若固定文字本身就是外部契约，说明依据及范围；状态码、命令名、协议字段、机器元数据和明确要求的固定文案可以精确断言。不要按“使用字符串”机械删除有效测试。
- 规则决策优先复用少量有区分力的既有样例，输入与评估标准分开；不能用同义词词典或更多关键词匹配充当语义评估。可执行结果仍应从实际入口验证，不靠模型声称成功。

## 验证与审查

在既有验收表说明所用方法实际证明的结果、未执行项和边界，不新建一套成功标准。行为证据缺失时如实记录 blocked/not_run，不能把文本检查改写为行为 pass。

Reviewer 核对测试的观察力和契约依据；不以断言数量或绿色套件代替必要证据。只有措辞匹配而缺少适用行为证据时，按现有合同判断证据缺口或具体缺陷；不要通过要求保留原句、堆更多匹配测试来解决。无关票不因此强制清理全部历史测试，已有充分证据也不机械重跑所有验证。
