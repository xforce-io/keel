# 何时写设计

L1 = 产品设计（做什么、怎样使用）；L2 = 技术设计（怎样可靠实现）。不是概要/详细两层，每份只写所需深度，不再拆子层级。触发条件由本文统一维护，不以 AGENTS.md 的「L1 触发」旧清单替代。章节结构、路径与项目规则的兼容方式见 [设计合同](../../keel-design/references/design-contract.md)。是否取得产品确认由 `when-to-ask.md` 判断，不把“需要写”当成“需要重复问”。

## 必须写 L1（任一）

- 新增或改变用户/外部调用方可见的能力、入口、交互、默认行为、权限结果或生命周期。
- 修改既有产品规则、适用范围或产品验收标准。
- 用户明确要求产品设计。

Web / 桌面 / CLI / TUI / 对外 API 都有产品行为，不以“没有图形页面”跳过 L1。按已有产品契约修复偏差，可以引用既有 L1 与对应验收，不为每个 bug 重写一份。

## 跳过写 L1

- 纯内部技术改造，产品行为与验收不变：明确引用不变的外部契约。
- 无行为变化的文案/文档、测试-only、开发依赖、单模块重构或运维变更。
- 已有覆盖本次范围的有效 L1：复用其版本与验收编号；有差异只更新对应内容。

“改的是文档/Skill”不自动属于纯文档：若改变 agent 对用户的工作行为或验收规则，仍需产品契约。信息不足时先补产品定义，不用 L2 代替缺失的 L1。

## 必须写 L2（任一）

- 新增/改变公共接口、协议、存储形态、跨模块责任、生产依赖或用户进程。
- 身份、权限、隔离、一致性、故障恢复、迁移等需形成可评审技术契约。
- L1 或用户明确要求技术设计。

L2 可以单独存在：纯技术改造引用不变的产品契约，不强行补 L1。用户可见变更须先落实适用 L1，再开始 L2；允许提前只读调研技术可行性。

## 跳过写 L2

- L1 行为明确，沿用已存在且适用的技术机制，没有新的技术契约。
- 纯文档/文案、测试-only，或无新契约的单模块改动。
- 已有覆盖本次范围的有效 L2：复用版本，必要时增量修订。

结果必须逐份记录 `L1: write|reuse|skip`、`L2: write|reuse|skip` 及依据。两份都不适用时直接执行适用 Issue 验收，不造空文档。L1-only 不需要虚构 L2 测试计划；其 L1.8 同样须提供完整产品验证依据。
