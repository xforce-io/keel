# 何时问人

只按本表匹配，不临场发明一类「感觉要问」。
keel 任务里要不要问人以本文为准，不以 AGENTS.md「评审通过后实现」为准。

必须问（缺授权则停）：

- force-push 到共享分支
- 合入默认分支（授权=审查 PASS 且人工门已满足（human: optional，或 required 已有当前候选的真实批准），或人明确说合入）
- 部署
- 删生产数据
- 对客消息

默认不问（做完呈交，人事后纠偏）：

- 写代码、改测试、改文档
- 测试-only / 开发依赖
- 验证用浏览器或模拟器（Drive 结束即关）
- 开 feat/* 或 bugfix/*、开 PR
- 团队聊天、改 Issue / PR 评论、跑检查

吃不准是否落在「必须问」→ 停，问一次。
「必须问」以外不得以操作审批为由停；产品定义是否明确按下节判断，这是范围确认，不是另一套操作审批。

## 产品基线确认

- 新增或改变产品行为时，L1 与 L1.8 必须明确，并有用户对相应范围的真实确认，才能进入 L2 或实现。可以是既有文档批准、Issue 中明确决定或本次会话确认，不要求再走一次平台批准。
- 已确认且覆盖本次变化的产品约定，可以整理成 L1 并直接复用确认来源；不因为文档刚生成就重复询问。仅技术变更、修复到已确认契约或纯文字整理不重新确认产品。
- 若只是“开发/端到端做完”，并未明确新增产品取舍，不能当成对 agent 后来新定的入口、范围或验收的提前批准。先写出具体可评审的 L1，再只询问尚未决定的产品问题；独立的技术调查可继续。
- 产品行为、范围或必需验收发生实质变化时重新确认受影响部分；技术实现选择不改变产品契约则不增加产品确认。
- L2 在已有明确产品基线上按需完成；dev/end-to-end 不额外等待一轮 L2 批准，除非用户或有效项目规则明确要求。design 模式交付所请求设计后结束，不自行实现。
- 产品确认与独立审查后的 human_approval 是两种依据，不能互相替代。确认必须留有真实来源和适用版本，不能由 coding agent 自签。

## 和其它门禁

四件事分开问，不要合成一个「要不要人」：

| 问 | 机制 | 谁判 |
|---|---|---|
| 现在能不能动手 | 上文两张表 | 按表匹配；吃不准就问 |
| 要不要写 L1/L2 | `when-to-write.md` | 写不写 ≠ 问不问 |
| 能否进入技术设计/实现 | 先满足上节产品基线；之后 design 交回，dev/end-to-end 继续 | 已有确认直接复用，不重复询问 |
| 合入前要不要人看审查 | `keel-review` 的 `human: required` 或 `human: optional` | Reviewer；硬条件不得 `optional` |

本表「合入默认分支」的授权就是审查 `PASS` 且人工门已满足（`human: optional`，或 `required` 已有当前候选的真实批准；也可由人明确授权合入）。`keel-design` 不另给 `human:` 字段。
