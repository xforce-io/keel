# Issue 产物与优先级

只在 `keel-reflect` 的 Backlog 里存在产品 Issue 候选时读取本文件。Issue 用于跟踪尚未解决的
项目结果，不用于保存泛化经验或代替当前已批准工作的交付。创建前必须经用户批准精确草案。

## 准入与合并

候选必须同时满足：

1. **项目归属明确**：问题属于当前仓库的产品、代码、测试、设计、文档或运维契约。
2. **有可核验证据**：来自已观察失败、复现、日志、测试、差异、用户反馈或缺失契约。
3. **尚未闭环**：当前任务没有解决它，且它不是当前 Issue 已覆盖但尚待继续执行的验收项。
4. **结果可判定**：可以写出独立的闭环结果和验收标准，而不只是“研究一下”或实现 TODO。

同一根因或同一闭环结果的候选合并为一个 Issue。不同根因不得为了减少数量而强行捆绑。
临时工具故障、个人环境偶发问题、纯 Agent 行为偏差或已经修复的问题不得生成 Issue；其中
可复用的 Agent 行为偏差转入指令通道。

## 优先级

根据已验证的影响、紧迫性、受影响范围和绕行方案，选择最高**有证据支撑**的级别：

- `P0`：正在发生的安全事件、数据损坏或生产事故，需要立即止损。
- `P1`：阻断发布、验收或核心用户路径，且没有合理绕行方案。
- `P2`：有明确业务或工程影响，但范围有限或存在可接受的临时绕行。
- `P3`：非阻断的维护性、体验、效率或文档改进。
- `UNDETERMINED`：关键影响证据缺失，当前不能可靠排序。

`P0`、`P1` 必须引用直接的当前影响证据。不得因问题复杂、修复成本高、出现次数多或主观重要
而提高优先级。`UNDETERMINED` 不是最低优先级；它表示需要补证据，须与已排序候选分开列出。

## 去重

先检查当前 Issue 或任务是否已经覆盖该结果。检查器提供托管平台线索时，按生效的
`AGENTS.md` 托管规则使用只读平台查询搜索开放和近期关闭的同类 Issue；比较根因、范围与
验收结果，不只比较标题。

无法访问平台、缺少 origin 或无法判定托管类型时仍可生成草案，但必须标记
`deduplication: unverified` 和缺失原因。发现同类 Issue 时，不新建草案；输出已有 Issue 的
关联建议或补充建议。

## 草案与人工门禁

每个通过准入的候选按优先级排序并包含：

- `priority` 与一句证据化理由；
- `deduplication`：`verified-new`、`existing` 或 `unverified`；
- 符合当前生效 `AGENTS.md` 的 Issue 标题、类型标签建议和完整正文；
- 支撑判断的最小证据，不包含原始会话、秘密或个人数据。

Stories 与验收标准必须一一对应。优先级是 reflection 的排序信息；除非仓库已有对应标签，
不得擅自发明平台优先级标签或把优先级塞进不允许的 Issue 正文节。

默认只展示草案。创建或更新 Issue 前必须获得用户对该精确草案的明确批准，并在写入前重新
检查 origin、托管平台和重复项。创建完成后报告结果并停止；修复、开发、MR/PR、合并与部署
由后续单独授权的 `keel` 流程处理。
