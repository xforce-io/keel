# 产品概念建模方法

借鉴 BKN Foundry 的对象类、关系类、行动类和风险类。先从实际产品路径提取并校正四类定义，再用同一套本体表达核心业务流程。 [BKN 引擎手册](https://github.com/openbkn-ai/bkn-foundry/blob/main/help/zh/manual/bkn.md)

1. 选一条主路径和一条有差异的路径。第二条可以改变同一对象的角色、复用已有对象或触及失败。已有产品先核对术语与事实来源，把拟新增的语义标为提案。
2. 按四类定义记录实际含义。

   | 类别 | 要回答的问题 |
   | --- | --- |
   | 对象类 | 一个实例代表什么？事实从哪里读取？什么变化会产生新的实例或版本？ |
   | 关系类 | 哪个对象以什么角色关联哪个对象？关系何时建立，能否缺省或重复？ |
   | 行动类 | 谁可以对哪个对象做什么？需要什么输入和前置条件？会改变或产生什么？ |
   | 风险类 | 行动在什么条件下可能造成什么后果？何时阻断、要求确认或提示？失败后如何处理？ |

3. 用第二条路径检查对象边界。同一实例只改变用途时，用关系表示角色。同一生命周期里的变化用状态表示。需要独立身份、查询、授权或追溯，且现有对象和关系无法表达时，再拆出新对象。
4. **用本体表达核心业务流程。** 从触发事件到可观察的终点，按实际顺序标明行动、关键等待状态和状态变化。行动描述谁做了什么，事件说明何时触发或可以继续，状态说明对象处于什么阶段。标明关键步骤的作用对象、使用或建立的关系，以及让流程继续的产出或条件。用风险约束解释分支条件、阻断时保留的状态和恢复去向。触发、等待和结果就绪可直接作为流程节点。
5. 把对象关系、核心业务流程和产品规则写回已有章节，并核对受影响的验收。流程图复用与该路径有关的定义，规则与验收沿用原有落点和编号。跨需求复用的模型由项目维护一份。
6. 工作流要求 HTML 时，在同一页提供可直接定位的对象关系和核心业务流程。两处复用同一套术语，流程呈现触发、行动、关键等待或状态变化、可观察结果及风险分支。页面随正文和相关验收一起维护，落点按当前工作流约定。

例如，「训练完成」触发登记，授权人员**登记模型**后得到模型版本。评估人员**提交评估**时引用同一版本作为基线，校验通过后建立基线关系并发起评估。无权引用时保留草稿供改选。提交后等待评估结果，系统产出结果后进入「结果就绪」，此时才能**查看比较结果**。同口径时展示差异，口径不一致时说明无法直接比较。登记产物和评估基线是同一个模型版本承担的两个角色。
