# 按需澄清

用于具体设计草稿中的未决产品取舍。触发与设计适用性见 [设计 skill](../SKILL.md)；确认和推进只认 [何时问人](../../keel/references/when-to-ask.md)，不新增批准门。

## 先分清所缺内容

- **已有决定**：核对来源、适用范围及版本后直接复用；当前实现与产品约定冲突时分别说明，不能把实现当成用户的新选择。
- **可查事实**：利用已有 how 依据并查源码、资料或环境；缺相关机制依据时回 how 补充调查，不把可查问题交给用户。查不到时明示缺口和限制，不把假设写成已确认。
- **产品取舍**：不同选择改变入口、用户行为、默认值、权限结果、范围或必需验收，而且尚无有效决定，才需要用户选择。不改变产品契约的技术选型由 agent 处理。
- **体验判断**：需要看或操作才能决定的布局、反馈、流程，先明确待验证问题，取得原型或实际操作依据再讨论；缺依据时保留未决，其余独立部分可继续。不以口头猜测代替体验。

已有契约足够的修复可直接复用，不能以“小”忽略真实歧义，也不能因进入设计就强制访谈。用最小可评审草稿表达已知路径及选择的影响；未定处明确标注，不能先写成完整已定方案让用户照单接受。

## 按依赖分轮

每轮只问前提已确定、彼此独立的问题；需要本轮其他答案的问题放到后续。事实调查未完成时只等待依赖它的问题，其他独立问题可以继续。不要预先穷举所有后续问题，也不要为了减少轮数而猜测答案。

每题编号并指向草稿中的具体入口、路径、规则或验收结果，给出可比较的选项、推荐答案与主要代价。表述应让“接受推荐”含义清楚；推荐不是用户决定。用户可改范围、否定推荐、回答不知道或要求逐题交流；不知道、未回复和超时都不等于接受。

问完等待用户回答；不能替用户回答后继续依赖该决定的工作。收到回答后重算未决问题及依赖；上游改变时重新检查下游，不沿用已失效的前提。澄清局限于本次目标，范围外事项列明，不无限扩展访谈。

## 回答写回原契约

有影响的回答及时写回原事实源：产品行为归 L1，技术契约归适用 L2，术语归项目名词表。设计或 ADR 已记录的决定用引用，不复制到项目知识或新台账。没有适用新设计时沿用原契约和任务验收，不为留存回答造新文档。

保留数字、单位、默认值、顺序、权限、异常处理及禁止结果的原义。可独立判定的产品约束映射到 [L1.8](design-contract.md) 的适用验收；已有契约复用其编号。记录真实回答来源和适用版本，不把推荐、自拟摘要或测试中的脚本回复当真实项目用户批准。

用户修改上游决定时，同步检查受影响的入口、路径、规则、验收及适用 L2；保留修订对应，不让旧值仍作为有效承诺。只对实质变化部分按原规则确认，不重复索取未变范围的确认。

## 交回原流程

核对本次主路径、范围、权限和必需验收是否仍有关键未决；没有可问问题本身不能替代产品确认。未决部分不能进入依赖它的技术设计或实现；可独立调查的事实仍可继续。

已有真实确认覆盖当前产品基线时直接复用，不因整理新文档或访谈结束再问一次。只按原确认规则处理缺失或变化部分，再按用户原模式交回路由；design 模式的交付停点不变。
