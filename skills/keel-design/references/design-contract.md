# 产品与技术设计合同

## 1. 事实源与文档形式

- Issue 定义需求范围与粗粒度验收 `S1…Sn`；L1 定义完整产品行为与细化验收；L2 定义实现契约。三者互相链接，发生矛盾先解决，不让后写的文档默默覆盖上游。
- L1 不是摘要，L2 不重复产品正文；每份文档引用 Issue、状态、版本及关联文档。L2 必须引用本次采用的确切 L1 版本（或说明 L1 不适用及所沿用的产品契约）。
- 默认位置为 `docs/design/{issue}-{slug}/product.md` 和 `technical.md`。只有适用文档才创建；不另设“概要”“详细”文档。已有项目的路径与章节标题可保留，但须映射到下面的必需语义，尤其 L1.8。
- Issue 设计节只放短摘要及链接；评论用于提案、评审与决定，不再把完整 L1 仅放评论。没有新文档时引用已有事实源，不复制。
- 新稿是 Draft；产品确认的判定只认 `keel/references/when-to-ask.md`。记录真实确认来源与适用版本，不能自批 Approved。设计版本不能仅用“最新版”代替。
- 项目 AGENTS 若仍规定 L1=概要、L2=详细，明确指出冲突并提出迁移；用户本轮已明确授权新定义时按其指令更新项目规则。无此授权时不要静默覆盖或假称两套定义兼容。
- 名词沿用应用仓库 glossary。新增领域词同步维护；代码级步骤归 plan/PR，不让设计变成函数清单。

## 2. L1 产品设计大纲

章节编号固定语义如下；项目改标题时在文首给出映射。小改可以每节一两句，无关部分写 N/A 与原因，不为凑章节引入能力。

### 1. 背景与目标

关联 Issue，说明用户问题与可观察目标，不复制整个 Issue。

### 2. 范围与非目标

本次交付边界、前置能力与明确不做的工作。不能把本来要求提供的入口藏在“预配置”“管理员事先完成”里；确有外部前置时写明主体和可用依据。

### 3. 用户与产品概念

参与角色、用户对象与关系、谁能操作；现有词链名词表，不堆技术数据结构。

### 4. Product Interaction Overview / 产品交互总览

一张主交互图加必要说明，表达参与者、整体目标、关键交互和介入/失败分支，可引用 Story 编号。优先 Mermaid；简单单步变更可写 N/A 并链接未变总览。这里不画数据库或进程架构。

### 5. 信息架构与入口

页面/菜单/命令/API 入口、导航和上下文切换；用户从哪里找到对象、看到当前范围、如何返回。新用户从空状态开始的路径不能遗漏。图形产品不能用 CLI 列表代替页面设计。

### 6. Stories 与完整交互

沿用 Issue 的 S 编号；需要拆路径用 S1.a 等关联标识，不另造第二组含义不同的 S1。每条包含角色、前置、触发入口、操作、可观察反馈、成功终点与异常分支。明确关键输入/默认值/校验、保存/取消、权限不足、加载/空/错误/成功及恢复操作；仅写“配置后保存”不够。

复杂交互用流程图、线框图或可评审原型补充；空/错/成功等放在对应路径中，不另复制一份互相矛盾的状态清单。精确布局只在影响判断/操作时写，不预定无关像素。

### 7. 产品规则与边界

权限、默认行为、生命周期、冲突、版本及副作用的可见结果。产品活动不必一一变成互斥状态；说明保证与禁止结果，不预定数据库或实现算法。规则需要引用时使用稳定标识，例如 R1。

### 8. 验收与效果验证

见下节的强制验收合同。功能交付门槛与长期效果观察分开；技术测试不能替代用户路径，用户可见成功不能替代数据/权限规则。

### 9. 折衷与开放问题

产品选择、放弃项及未决问题。影响主路径、范围、授权或必需验收的问题必须在技术设计/实现前解决；允许记录未来探索，但不能把关键决策留给 coding agent 随手补。

## 3. L1.8 验收合同

每项可独立判定的产品验收使用稳定 ID：默认 `S1.A1`、`S1.A2`；既有项目 A 编号可以保留，但必须映射回 Issue S 编号。一个 Story 可对应多项验收，一个验收须有明确主要归属，不因拆分而丢失 Issue 的 1:1 Stories/粗粒度验收关系。

每项至少有以下字段；表格过宽时用分块表，不删语义：

| 字段 | 约束 |
|---|---|
| ID 与关联 | 稳定编号、Issue S、L1 Story 与适用规则；删除/改变要保留修订映射，不重用旧 ID 表示新含义 |
| 前置条件 | 身份、权限、数据、配置、外部依赖与版本 |
| 入口与操作 | 真实产品入口和完整步骤；不能用内部函数调用代替桌面/Web/CLI 路径 |
| 可判定结果 | 可观察的具体结果及必要持久化结果；“正常/友好/正确”不是标准 |
| 异常与禁止结果 | 失败反馈、后续处理、不能发生的行为；独立情形拆成独立验收行 |
| 证据要求 | 操作记录、截图、数据结果或原始输出应证明什么，不只写“测试通过” |
| 执行与依赖 | agent 可执行、需人工判断或需真实服务；给出真实验证与 mock 各自证明的边界 |
| 交付属性 | 必需验收，或后续效果观察；后续观察明确责任方、观察条件和判定时机，不能借此推迟必需功能 |

L1.8 只定义标准，不写本次执行的 pass。它与设计版本一起固定；验证表另记候选 SHA、设计版本、环境、时间和证据。

必需项结果使用 `pass / fail / blocked / not_run`。skip 只表示事先明确不适用，并引用有效依据；缺环境、未执行、缺人工判断不能改成 skip。必需项 fail/blocked/not_run、缺行或证据不足都阻止“全部完成”。后续效果观察可以保持待观察，但最终报告须列出，不能宣称价值已得到证明。

示例（不是实际验收证据）：

| ID / 关联 | 前置 | 路径 | 结果与禁止行为 | 证据 / 执行 / 属性 |
|---|---|---|---|---|
| S1.A1 / S1 / R1 | 模型连接不可用；用户有成员创建权 | 成员→创建→填配置→测试连接→保存→重新打开 | 成员保存为待配置，显示失败原因和修复入口；不显示可执行、不启动工作，重开后配置仍在 | 失败反馈、保存后详情与重开操作记录；agent 可执行，失败服务可确定性注入；必需 |

同一 Story 汇总 pass 必须覆盖全部适用必需验收，不能只验证一条方便路径。L1 无需指定测试框架，但必须给出可执行、可判定的验证路径。

## 4. L2 技术设计大纲

1. **设计依据与技术目标**：关联 Issue、L1 确切版本和验收 ID；L1 不适用则写原因与沿用产品契约。技术约束及非目标明确。
2. **现状与改动范围**：引用 keel-how 的源码依据，说明复用与改动责任；全新项目写无现成机制。
3. **总体架构与关键路径**：模块/进程边界、主路径与失败路径、选择及折衷。
4. **数据与状态契约**：身份、关系、事实源、持久化、版本、并发、不变量；不复制产品规则，说明落实机制。
5. **接口与协作契约**：API/CLI/事件/协议/配置、错误、重试、幂等与兼容。
6. **运行与保障机制**：认证授权、资源限制、取消、故障恢复与可观察性，影响结果的默认值、上限和时间边界明确。
7. **迁移、发布与回滚**：现有数据和行为兼容、引入变更与失败撤回；不适用写 N/A。
8. **测试与验证**：按 L1 验收 ID 映射 E2E、Integration、Unit，说明每项由什么机制保证、怎样取证；纯技术项可用 T1 等 ID，不能替换产品验收。
9. **技术风险与开放问题**：需验证的技术假设、依赖与限制；影响 L1 承诺时回到 L1，不在此暗中缩减。

有用户路径时，L2.8 点名应用仓库 `.agents/skills/verify-*/features/<file>.md` 或 README 条目，并映射 L1.8 验收。每个 S 指定一个主要功能文件，文件可覆盖多个验收和链接其他必要路径；不限制一个产品目标只能走一个入口。L2 省略时，这一映射随 L1.8 提供。

## 5. 交付链与变更

- 顺序：产品定义及 L1.8 明确 → 按确认规则形成产品基线 → 按需 L2 → 实现 → 对照标准验证。可先调查技术可行性，不能用技术方案倒推出未经确认的产品范围。
- 实现中发现产品不可行、范围变化或验收需变：记录差异，修订 L1/Issue 并取得适用确认，再更新 L2；不能先降低标准再报 pass。纯实现选型在不改变产品契约时可自行调整 L2 并解释。
- L1/L2 的版本与候选 SHA 独立记录；需求变化重审受影响验收，代码变化重跑受影响检查。不可把旧证据改个 SHA 当新证据。
- 开发给出候选测试表；keel-verify 从真实入口逐项取证；独立审查检查追踪、完整性和证据；release 核对所有必需项。每个环节引用同一基线，不维护自己的成功标准。

## 6. 兼容既有项目

不批量改写历史设计。接手任务时先判断旧文档是否已经覆盖所需产品行为和技术契约：完整的可以保持路径、补章节/验收映射并复用真实确认；只有概要不能因为标题叫 L1 就当成完备产品设计。新增或受影响内容迁移到本合同，历史事实不重写。

`keel check` 的 schema v1 本次不变：`design.evidence` 指向一份设计依据文件，列明 L1/L2 的 write/reuse/skip、版本/路径/摘要、确认来源、Issue S 到 L1.8 验收映射，以及技术设计对应关系；`design.version` 标识这份固定依据。L1.8 详细验证结果通过现有 stories/verify evidence 引用，S 行按全部必需子项汇总。

v1 校验器只校验索引及文件摘要，不解析 L1.8、不自动发现漏验收，也不认证产品确认。调用方、Reviewer 与 release 必须核对原始依据；不能宣称新语义已有机器强制门禁。未来若扩展 schema/CLI，应另作兼容设计与测试，不趁本次模板更新更改索引格式。
