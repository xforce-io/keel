# 技能产品拆分规则

只在 [设计 skill](../SKILL.md) 写明的条件下读取：本次要设计或修改的产品对象是 agent skill，且行为事实源是 `SKILL.md`。本次产品对象不是 agent skill 时不读本文件。仓库里仅仅存在一份 `SKILL.md` 不构成触发。

本文件不进入设计阶段的必读清单，不改共享的 L1/L2 大纲，也不掌管交付状态机或宿主路由。

## 规则

- 一个自动选用的入口 skill 写明适用场景、输入输出、方法、依赖的工具、合格标准与验证方式，且不掌管整次任务生命周期或宿主路由。
- 内部步骤留在普通参考里，不是 skill。
- 另立 skill 参考下节的拆分判断。各项是倾向拆分的依据，不要求同时满足，也不意味着命中一项就必须拆分。
- 换执行者时复用该 skill，不复制一份。
- 变体留在入口路由表。
- CLI、斜杠命令或 API 只限入口、参数和约束。
- 不建嵌套 skill 树。
- 验收写做对了是什么样，不写 skill 被调用了。

## 拆分判断

依据《Agent Skills、Playbook 与 Command 的架构设计建议》§2.1、§5.1。保留原文的判断维度和建议性质，不把它们改成全部成立才允许拆分的门槛。

| 判断问题 | 设计取向 |
|---|---|
| 是否有独立、稳定且可跨任务复用的专业方法？ | 倾向另立 skill，让多个任务复用同一方法。 |
| 是否有明确的输入和输出，可以定义能力契约？ | 适合考虑另立 skill。 |
| 是否需要独立评测，可以单独判断质量？ | 倾向另立 skill。 |
| 是否只在单一流程出现、非常简单且无明显复用价值？ | 保留为内部步骤，写在普通参考里。 |
| 是否只换执行角色，方法本身没有变化？ | 复用同一 skill，不按角色复制能力。 |

例：引用核验有独立、稳定的方法及输入输出，即使尚无单独评测需要，也可以考虑另立 skill；应在折衷节说明复用价值和边界。

反例：同一文档提取任务中的“提取摘要、方法、实验结果、结论”，若只服务这个流程且方法简单，不因有四个步骤就拆成四个 skill。换一个执行角色也不构成拆分理由。

## 拆分决定

应用本规则的那次设计，在 L1 折衷节记录拆分决定：哪些留在内部参考，哪些另立 skill，以及放弃了什么。
