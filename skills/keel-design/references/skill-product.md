# 技能产品拆分规则

只在 [设计 skill](../SKILL.md) 写明的条件下读取：本次要设计或修改的产品对象是 agent skill，且行为事实源是 `SKILL.md`。本次产品对象不是 agent skill 时不读本文件。仓库里仅仅存在一份 `SKILL.md` 不构成触发。

本文件不进入设计阶段的必读清单，不改共享的 L1/L2 大纲，也不掌管交付状态机或宿主路由。下列概念用于判断本次产品的职责归属，不要求新建注册表、运行时或固定目录。术语见 [名词表](../../../docs/glossary.md)。

## 先选职责，再选文件

这些抽象可以组合，不是整项任务只能选其中一个。

| 需要解决的问题 | 选择 | 必须定义的内容与边界 |
|---|---|---|
| 用户需要稳定、可发现的操作入口 | Command | 名称、参数、目标和约束；CLI、斜杠命令或 API 只限入口、参数和约束，不内嵌完整流程或专业方法。 |
| 一类完整任务需要多个步骤协作，且阶段和交付标准可以复用 | Playbook | 目标、输入、交付物、阶段、依赖、检查点、完成标准、审批点，以及可选步骤、分支和失败回退；引用 Skill，不复制方法。 |
| 一项专业方法需要跨任务复用，或具有独立契约、质量判断价值 | Skill | 适用场景、输入输出、方法、依赖的工具、合格标准与验证方式；不掌管整次任务生命周期或宿主路由。 |
| 较大能力中有一个更窄、仍可独立复用和判断质量的方法 | Subskill | 按同一套 Skill 拆分标准决定是否独立；Subskill 不是新增层级，不因属于某个流程就成为子能力。 |
| 需要独立上下文、并行执行、不同模型或不同权限 | Subagent | 执行者的上下文、模型、权限及任务边界；换执行者时复用该 skill，不复制一份。 |
| 执行路径要根据证据缺口、中间结果、预算或风险调整 | Orchestrator | 选择、重排、补充、回退和停止条件；Playbook 提供默认路径，不替代当次决策，也不绕过已明确的审批和安全约束。 |
| 需要持久状态、审批、审计或可靠重试 | Runtime | 用系统能力实现状态与执行保障，不能只写在提示词里。 |
| 需要判断专业能力、流程或最终交付是否有效 | Eval | 输入、预期结果及证据；验收写做对了是什么样，不写 skill 被调用了。 |

## 拆分判断

各项是倾向拆分的依据，不要求同时满足，也不意味着命中一项就必须拆分。

| 判断问题 | 设计取向 |
|---|---|
| 是否有独立、稳定且可跨任务复用的专业方法？ | 倾向另立 Skill，让多个任务复用同一方法。 |
| 是否有明确的输入和输出，可以定义能力契约？ | 适合考虑另立 Skill。 |
| 是否需要独立评测，可以单独判断质量？ | 倾向另立 Skill。 |
| 是否只在单一流程出现、非常简单且无明显复用价值？ | 内部步骤留在普通参考里，不是 skill。 |
| 是否只换执行角色，方法本身没有变化？ | 复用同一 Skill，不按角色复制能力。 |

Subskill 采用同样的能力契约、版本维护和评测要求。多个 Skill 可以互相引用；不建嵌套 skill 树，不靠父子路径决定调用顺序、继承权限或管理生命周期。只有标题更细、只在本流程出现的简单动作，应留作内部步骤。

例：引用核验有独立、稳定的方法及输入输出，即使尚无单独评测需要，也可以考虑另立 skill；应在折衷节说明复用价值和边界。

反例：同一文档提取任务中的“提取摘要、方法、实验结果、结论”，若只服务这个流程且方法简单，不因有四个步骤就拆成四个 skill。换一个执行角色也不构成拆分理由。

## 流程、变体与执行边界

- 多个 Skill 协作完成同一类任务时，用 Playbook 表达阶段与依赖；专业方法留在各自 Skill。Playbook 引用 Skill，不复制 Skill 正文。
- 不为每种主题、资料类型或步骤组合新建 Playbook。相同交付契约下的小变体，用现有 Playbook 的参数、可选步骤或分支表达；只有目标、阶段结构或交付标准发生实质变化，才考虑另立 Playbook。
- 同一方法的输入格式或策略差异，留在 Skill 的参数或方法分支中；独立方法再按拆分表判断，不把所有变体塞进入口路由表。
- 仅需复用方法时不新增 Subagent；需要隔离或并行时选择执行主体，不能用复制 Skill 实现角色切换。
- 静态路径已足够时无需引入动态编排。确需根据结果调整时，由 Orchestrator 决策；持久化、可靠重试和审批执行交给 Runtime，不让 Skill 承担系统状态管理。

例：研究任务由 Command 接收主题，Playbook 组织检索、来源评估、证据综合和交付；各项方法由 Skill 提供。来源评估作为较窄能力时可称 Subskill，但仍是同一种能力资产。遇到结论冲突，由 Orchestrator 决定补查或回退；只有需要独立反证上下文时才交给 Subagent，复用已有核验 Skill。

## 验证与拆分决定

按实际设计涉及的层次定义验证，不强制新增评测目录或平台：

- Skill / Subskill：验证方法执行、输出质量和已有能力回归，保留样例输入、预期结果及工具记录。
- Playbook：验证阶段覆盖、依赖、检查点、顺序及异常分支。
- 最终任务：验证交付物、用户目标，以及已约定的成本和耗时要求。仅有调用成功或阶段全部结束不足以判定达成目标。

应用本规则的那次设计，在 L1 折衷节记录拆分决定：每个主要职责选择哪种抽象，哪些留在内部参考，哪些另立 Skill / Subskill 或 Playbook，执行主体和运行保障是否必要，以及放弃了什么。写明判据，不只列文件名。
